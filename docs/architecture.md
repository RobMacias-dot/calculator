# Decisiones de arquitectura

## 1. Separación y MVVM

La organización es feature-first. `app` compone el sistema y contiene toda la navegación. `core/design_system` concentra el lenguaje visual. `features/calculators/domain` es Dart puro: no importa Flutter, navegación, estado ni I/O.

Home transforma consulta, filtro de categoría y sección seleccionada en resultados mediante `HomeViewModel`. La dirección del estado es UI → acción del ViewModel → notificación → UI. `ChangeNotifier` pertenece a presentación, no al dominio. Las páginas que solo muestran metadatos reciben modelos inmutables; no se añade un ViewModel sin responsabilidad. El tema se expone mediante un `ValueListenable<ThemeMode>` independiente dentro de `PreferencesController`.

Los formularios usan `CalculatorViewModel`, una clase pequeña sin fórmulas ni switch por calculadora. Posee valores crudos, unidades, objetivo y estado (`idle/success/invalid`), y recibe operaciones por composición. Cambiar entrada/unidad invalida el resultado; cambiar objetivo o Reset limpia el formulario. Cada pantalla posee y dispone su ViewModel. Los widgets solo capturan y presentan datos.

`main` inicializa Flutter y restaura preferencias antes de `runApp`. `EngineeringToolkitApp` recibe registro y controlador, compone Home/router y asume la disposición de los objetos de presentación al terminar. No hay service locator ni singleton mutable. Los temas compartidos son configuración inmutable.

**Persistencia pequeña y explícita.** `PreferencesRepository` lee/escribe snapshots inmutables de tema e IDs. `LocalPreferencesRepository` es la única clase que importa `shared_preferences`; usa `SharedPreferencesAsync` y un JSON bajo la clave versionada `engineering_toolkit.preferences.v1`. No hay acceso al storage desde widgets. Los tests sustituyen repositorio y API de storage por implementaciones en memoria. El registro sigue siendo catálogo, sin I/O.

`PreferencesController` mantiene solo tema/favoritos/recientes y estado de fallo; no absorbe navegación, búsqueda ni formularios. Resuelve IDs contra el registro, descarta desconocidos, deduplica y limita recientes a cinco. La apertura del formulario registra el reciente una vez, después del primer frame, también en enlaces directos. Cambios de tema se observan en `MaterialApp`; favoritos/recientes notifican a sus consumidores sin reconstruir toda la app. Se conserva inyección por constructores: `provider` no reduciría wiring suficiente para justificar otra dependencia.

La lectura tiene timeout de dos segundos; error de I/O/JSON utiliza System y listas vacías. Tipos de campos inválidos se ignoran conservando los válidos. No se aplica una lectura tardía sobre acciones de la sesión. Las escrituras de snapshots se encolan para impedir inversión del orden; sus fallos se capturan sin revertir la UI ni romper la cola. Settings presenta un aviso no técnico, que desaparece al volver a guardar. Las acciones siguientes reintentan el snapshot completo; no hay reintentos en background ni garantías para datos críticos/cierre abrupto.

## 2. Registro y cálculo determinístico

`CalculatorDefinition` conserva ID estable, nombre, categoría, explicación, supuestos, entradas, modos y keywords. Cada modo tiene sus campos y un callback explícito. El ID identifica metadatos, no una expresión matemática. Los motores reciben parámetros nombrados tipados. La categoría sigue sirviendo como identificador visual. Las colecciones y los metadatos capturados por callbacks se copian; se rechazan IDs de modo/campo duplicados y listas de unidades dimensionalmente incompatibles.

El lookup por ID usa un mapa; las listas de resultados son inmutables. La búsqueda recorre nombre, descripción, categoría y keywords con normalización de mayúsculas, espacios, apóstrofos y acentos latinos comunes (incluidas marcas combinadas). Todos los términos deben coincidir; no hay fuzzy search ni transliteración universal. Home/Tools comparten esa búsqueda. Las listas de herramientas son lazy; las seis categorías usan un Wrap adaptable y de altura natural. No se necesita un índice de búsqueda ni carga dinámica para este tamaño.

Pipeline implementado: **texto → parser → validación de sintaxis/finitud → conversión SI/base → validación física y motor puro → resultado tipado → unidad mostrada/formato/reporte → UI**. `numericMode` comparte esa coordinación para resultados escalares. `parseNumericInputs` extrae el parsing y conversión que también necesitan resistencias y quadratic; no evalúa ecuaciones. Networking tiene adaptadores enteros específicos. Las funciones de `engines/` no conocen Flutter ni presentación. Fórmulas, sustitución y explicación se construyen mediante plantillas determinísticas después del cálculo. No hay IA, CAS, DSL ni evaluación de strings.

`ResistorMode` cubre exclusivamente las dos redes de resistencias. El ViewModel coordina una lista de campos, conserva entradas y unidades al añadir/quitar el último y nunca permite menos de dos. Reset vuelve a dos; modificar la lista invalida el resultado. No hay máximo artificial ni framework de formularios dinámicos. El motor recibe una lista de valores base y valida cada resistencia. Series permite cero; Parallel exige valores positivos y escala las conductancias para evitar desbordamientos innecesarios.

`QuadraticRoots` describe dos raíces reales, una repetida o un par conjugado con cuatro campos; no ofrece álgebra compleja. El motor escala coeficientes y usa la formulación estable con q para evitar cancelación al obtener raíces muy desiguales. El reporte y la copia usan la etiqueta explícita `Roots`; `resultLabel` es opcional para preservar el comportamiento anterior.

`CalculationOutcome<T>` es una unión sellada: `CalculationSuccess<T>` o `CalculationFailure<T>` con una lista inmutable de `CalculationIssue`. Los errores distinguen campos ausentes, sintaxis, división por cero, dominio físico, no finitos, rango numérico y unidades incompatibles. Se acumulan errores de campos. No se lanzan exceptions para validación habitual; `ArgumentError` queda reservado a definiciones mal construidas/programación incorrecta. `CalculationResult` es el reporte independiente de Flutter: valor numérico sin redondear cuando aplica, unidad tipada, valor mostrado, fórmula, sustitución, explicación y notas/detalles.

### Unidades y precisión

`EngineeringUnit` enum centraliza dimensión, símbolo, escala y desplazamiento; no es un motor universal de análisis dimensional. La selección se comprueba contra las unidades permitidas de cada campo. `toBase` es puro: `valor × escala + desplazamiento`; °C suma 273.15, no usa una conversión solo multiplicativa. `fromBase` implementa la inversa con validación de rango. `CalculationResult.value` conserva el valor base; su unidad y texto mostrado describen la presentación. `numericMode` convierte a la unidad declarada y puede añadir equivalencias de la misma dimensión como detalles. No hay selector general de unidades de salida. Cambiar una unidad reinterpreta la cifra introducida; no convierte automáticamente el texto del formulario.

Phase 4 añade solo dimensiones y unidades utilizadas por herramientas concretas. Temperatura absoluta (K/°C/°F) y diferencia de temperatura (ΔK/Δ°C) son distintas: las diferencias tienen escala uno y cero desplazamiento. El porcentaje usa escala 0.01; eficiencia y cambios porcentuales se calculan como fracciones y se presentan en %. Potencia, energía, tiempo, área, caudal, torque, momento, calor específico y coeficiente de expansión comparten el mismo enum y pipeline.

`NumberParser` acepta signo, punto o coma decimal y notación científica, sin agrupación de miles. Rechaza NaN/Infinity, overflow y underflow a cero. Los motores validan de nuevo sus argumentos públicos y comprueban el resultado; la igualdad exacta con cero es deliberada para divisores, sin tratar números pequeños válidos como cero.

`NumberFormatting` limita la presentación a seis decimales, elimina ceros finales y usa notación científica para magnitudes no nulas menores de 1e-6 o desde 1e9 (seis decimales de mantisa). NaN/Infinity no se presentan como resultados válidos. No se redondea dentro del motor. Las pruebas comparan con tolerancia relativa 1e-10 y absoluta 1e-12, y usan igualdad exacta cuando verifican enteros/ceros. Los extremos de `double`, incluidos resultados intermedios no representables, producen errores explícitos; no se promete precisión arbitraria.

Convenciones físicas: Ohm modela resistencia pasiva no negativa, permite V/I con signo compatible y exige divisor positivo/no nulo según objetivo; R=0 solo es admisible fuera del divisor. Newton admite masa cero y aceleración con signo. Reynolds usa magnitud de velocidad no negativa y no clasifica regímenes de forma universal. Gas ideal usa estados no vacíos con P/V/n/T estrictamente positivos, presión absoluta y R=8.31446261815324 J/(mol·K).

Torque supone fuerza perpendicular; Work supone fuerza paralela. Momentum admite velocidad con signo. Hidrostática usa presión manométrica y g = 9.80665 m/s². Bernoulli resuelve únicamente P2 para flujo estacionario, incompresible, sin viscosidad, sobre una misma línea de corriente, sin bombas/turbinas ni pérdidas; admite presión con signo referida al mismo origen y no predice cavitación. Sensible Heat supone calor específico constante y ausencia de cambio de fase. Eficiencia exige Qin > 0 y 0 ≤ Wout ≤ Qin; temperatura absoluta permite 0 K pero no valores inferiores. Expansión lineal permite enfriamiento y coeficiente negativo, rechazando una longitud final no positiva. Estas condiciones aparecen en las definiciones y en el formulario, no solo en documentación.

### IPv4 entero

El parser exige cuatro octetos decimales canónicos 0..255 (sin ceros iniciales), y un prefijo entero 0..32 sin `/`. Direcciones, máscaras, rangos y conteos usan `BigInt` y operaciones bitwise; solo octetos y prefijo usan `int`. No se usa `double`, `pow` ni conversiones a punto flotante. Así `/0` conserva 4294967296 direcciones incluso en JavaScript, cuyas operaciones bitwise nativas tienen particularidades de 32 bits.

`/0–/30` aplica total−2; `/31` usa ambos extremos punto a punto según RFC 3021; `/32` representa una sola dirección. El resultado separa el último valor del rango de un broadcast dirigido: para `/31` y `/32`, `broadcastAddress` es nulo y la UI lo indica. El reporte advierte que una cuenta matemática no garantiza asignabilidad/ruteabilidad de direcciones reservadas.

Las tres herramientas nuevas reutilizan el parser IPv4: representación binaria exige cuatro grupos de ocho bits, máscara/CIDR verifica contigüidad y Wildcard invierte una máscara válida. Las 33 longitudes de prefijo tienen pruebas de ida y vuelta. No se añadieron operaciones de punto flotante ni VLSM.

## 3. Navegación

`go_router` implementa exactamente `/`, `/category/:categoryId`, `/calculator/:calculatorId` y `/settings`. Las vistas reciben callbacks; no importan el router. El Shell conserva el marco y la navegación inferior. Categorías y calculadoras usan push/pop para admitir Atrás del sistema; una entrada directa dispone de un regreso explícito a categoría/Home. IDs inexistentes y rutas desconocidas presentan recuperación sin excepciones técnicas.

Home, Favorites y Tools siguen siendo secciones locales del mismo Home. Favorites resuelve IDs guardados contra el registro y ofrece exploración cuando está vacío; Tools es el catálogo completo con búsqueda y categoría. Conservan consulta/filtro durante la sesión; no prometen URLs o historial independiente de pestañas. Settings tiene su ruta propia. Solo tema, favoritos y recientes se restauran después de cerrar la aplicación; los formularios y la navegación no.

## 4. Diseño, accesibilidad y rendimiento

Material 3 con tokens para color, espacio, radios, tipografía, sombras y duración. Naranja reservado para acentos y acciones. Tema claro prioritario, oscuro disponible. No se descargan fuentes ni recursos gráficos durante la ejecución móvil.

Las tarjetas usan relleno translúcido y una sombra ligera sin filtros. Hay **un único BackdropFilter**, recortado a la cápsula inferior. La altura de tarjetas es natural; los formularios son desplazables y los selectores permiten altura variable. El teclado reduce el viewport y oculta temporalmente la barra inferior. Las anchuras estrechas o texto ampliado reducen columnas; a texto grande la barra conserva iconos, tooltips y etiquetas semánticas. Al calcular, el scroll lleva al resultado o al primer error; ambos usan anuncios semánticos donde corresponde.

La navegación inferior expone etiqueta, selección y acción accesible. Favoritos utiliza estrellas, estado seleccionado y tooltips con nombre de herramienta en catálogo, categoría y formulario. ResultCard copia nombre, resultado y sustitución con `Clipboard` del SDK y confirma mediante SnackBar; validación sigue inline. Targets de al menos 48 px, estados explícitos y contraste mediante ColorScheme. Las animaciones respetan la preferencia de movimiento reducido. Se prueban targets y contraste en ambos temas, además de texto al 200%; esto no sustituye revisión con TalkBack/VoiceOver real.

## 5. Dependencias y pruebas

Flutter ofrece estado observable y composición suficientes para esta fase; `provider` se reserva para cuando reduzca complejidad real. `go_router` elimina código manual de parsing y coordinación de Navigator. Se conserva el lockfile, incluidas sus dependencias transitivas. `flutter_lints` más inferencia/casts/tipos estrictos y control de futuros sin esperar, sin excepciones para ocultar warnings.

Pruebas en tres niveles: metadatos/motores, estado del ViewModel y flujos de widgets. Los casos numéricos viven en archivos Dart sin Flutter: los ejecutan tanto `flutter test` como `dart run tool/test_domain.dart`, sin añadir otro paquete de tests. El mismo conjunto puede ejecutarse con `flutter test --platform chrome test/domain/calculation_test.dart`. Las pruebas heredadas conservan navegación, enlaces directos, recuperación, búsqueda, tema y Atrás; se añadieron los cinco flujos completos, unidades, selección de objetivo, reset, teclado y texto al 200% en claro/oscuro. Las excepciones de layout no se silencian.

## 6. Crecimiento y límites

Una herramienta nueva se registra una sola vez; router, búsqueda y conteos se derivan del catálogo. Al crecer, cada definición y estrategia puede vivir en su módulo de categoría, ensamblado explícitamente en el arranque. Se extraerán componentes compartidos solo después de conocer usos reales. El registro no debe convertirse en un contenedor de estado de formularios.

Pendientes deliberados: historial de resultados, unidades de salida seleccionables, compartir por sistema y localización completa. Pendientes de distribución: iconos propios, ID de producto definitivo, firma de release y verificación nativa en iOS/Android. La plataforma web es una facilidad de desarrollo, no una promesa de PWA offline. No hay autenticación, backend, telemetría ni secretos. Phases 4 y 5 añaden cero dependencias; Phase 6 no está implementada.

### Revisión de escala de Phase 4

- 30 herramientas, ensambladas en una lista explícita de unas 47 líneas; `CalculatorRegistry` conserva sus 55 líneas. Categorías, búsqueda, favoritos, recientes y rutas resuelven ese único registro. No se añadieron conteos de producto hardcoded.
- Las nuevas definiciones y motores suman aproximadamente 2000 líneas: **80 líneas por herramienta nueva**, excluidos tests e infraestructura compartida. La repetición restante es metadatos de campos y texto educativo específico; se mantiene explícita para poder revisar fórmulas y unidades.
- El ViewModel tiene unas 130 líneas y un switch de resultado. La nueva responsabilidad es coordinar la lista de resistencias; no contiene matemáticas ni switches por ID. Los nueve switches del dominio resuelven parsing/conversión, tipos de resultado y convenciones IPv4; ninguno despacha un catálogo creciente.
- El enum de unidades tiene unas 129 líneas. Parsing/conversiones se comparten entre escalares, resistencias y quadratic; las comprobaciones físicas comunes se extraen solo donde existen usos reales. No hay conversiones duplicadas en widgets.
- Los casos de dominio nuevos usan tablas de ejemplos independientes y verifican todos los modos; los flujos de widgets se eligen por estructura, sin repetir un flujo por fórmula equivalente. Se conservan los 207 casos previos mediante una fixture de catálogo histórico y se comprueba además el registro de producción completo.
- Home, Tools, Favorites y categorías mantienen listas lazy; las tarjetas no añaden filtros de desenfoque. Permanece un único `BackdropFilter` en la navegación inferior. El formulario dinámico monta todos sus campos: si aparece un uso real con cientos de resistencias editables, medirlo antes de introducir virtualización.

**¿La calculadora 26 es aproximadamente igual de sencilla que la 6? Sí para un resultado escalar:** motor puro, definición, registro y casos de dominio. El coste depende de la estructura de entrada/resultado, no del número del catálogo. Quadratic y las redes requieren adaptadores pequeños; no obligan a cambiar router, búsqueda ni un switch central. No se justificó un refactor general. El procedimiento mínimo está en “Adding a new calculator” del README.

La deuda relevante sigue siendo validación nativa, bootstrap del runner Chrome y límites de precisión `double`. JavaScript/Node cubre semántica numérica, sin reemplazar renderizado web. Las capturas de Phase 4 revisan supuestos, raíces complejas, energía y resistencias en ambos temas. Las métricas anteriores corresponden al cierre de Phase 4; Phase 5 incorpora únicamente la capa visual descrita a continuación.

## Visual Learning Architecture

**Propósito.** Cuatro pilotos demuestran representaciones distintas sin convertir la app en un simulador. `CalculatorDefinition.supportsVisualLearning` es una capacidad opcional del registro existente: no duplica IDs, nombres, categorías, rutas o fórmulas. No hay un segundo registro. `CalculatorScreen` ofrece una acción secundaria, deshabilitada sin un cálculo válido. `showModalBottomSheet` construye la escena solo al abrirla, manteniendo montado el formulario y su ViewModel; no se modificó el router.

**Pipeline y responsabilidades.** El dominio conserva opcionalmente un `CalculationContext` inmutable en `CalculationResult`: entradas normalizadas y sus descriptores tipados para divisor/vector/flujo, o el `Ipv4SubnetResult` exacto. Las definiciones ensamblan estos datos después de la validación y del motor; no cambia ninguna fórmula. `numericMode` recibe un callback opcional que empaqueta entradas ya convertidas. Ninguna clase de dominio importa Flutter ni geometría de pantalla.

`presentation/visual_learning/visual_models.dart` transforma esos datos y el resultado principal existente en modelos inmutables. Solo realiza matemática visual: normalización, proyección, cocientes de valores ya calculados y escalas gráficas. No parsea textos formateados ni invoca motores. El renderer recibe el modelo, usa colores/tipografía del tema y dibuja. Quitar el renderer no cambia el cálculo.

Los controles convierten el valor base al selector de unidad actual con `EngineeringUnit.fromBase`, conservan precisión mediante `double.toString()` y llaman `CalculatorViewModel.updateAndCalculate`. Este método actualiza la misma entrada, ejecuta el callback del modo y refresca los campos al volver al formulario. Un fallo conserva los errores del motor y retira el modelo visual. Nunca se presenta el último resultado como si aún correspondiera a entradas inválidas.

**Pilotos.** Divisor: circuito sin carga con resistores de igual tamaño, Vin, R1, R2 y nodo Vout; la barra compara el resultado con Vin y no inventa un cociente para Vin = 0. Vector: modos 2D/3D existentes, escala por componente máxima y proyección oblicua explícita; la magnitud siempre viene del motor y una componente minúscula puede ser invisible sin perder su etiqueta. Reynolds: ilustración continua mediante un logaritmo acotado de Re entre 1 y 10⁶, declarado como escala artística, sin clasificación formal ni CFD. IPv4: bits obtenidos de la dirección validada, metadatos exactos del resultado entero y barra logarítmica de tamaño; no vuelve a calcular máscara, red, rangos o hosts.

**Primitivas compartidas.** Superficie modal, `VisualScene` para semántica/tamaño/repaint, `VisualInputControl` para tres pilotos, etiquetas de diagramas para divisor/vector y detección de movimiento reducido. No se comparten leyes físicas ni un scene graph. El switch de cuatro tipos de modelo solo selecciona renderer, no operaciones matemáticas.

**Añadir una visualización.** (1) Reutilizar el resultado y, únicamente si falta información, retener un contexto tipado de datos validados en la definición. (2) Activar la capacidad en esa definición. (3) Añadir modelo/mapper y renderer en presentación, con geometría finita y supuestos explícitos; ampliar la selección exhaustiva de modelos. (4) Probar mapping, interacción con el pipeline, límites, accesibilidad y ciclo de vida cuando haya animación. No cambiar el router ni introducir un framework para anticipar escenas futuras.

**Rendimiento.** Divisor y vector usan `CustomPainter` estático; IPv4 utiliza 32 celdas normales. Reynolds tiene un único controlador, seis paths cacheados por tamaño/modelo y 24 puntos determinísticos. El `Listenable` repinta el canvas dentro de un `RepaintBoundary`; no hay `setState` por tick, creación de colecciones/paints/paths por frame ni cálculos del dominio. `shouldRepaint` compara geometría, estilo y fuentes relevantes. No se añadieron `BackdropFilter`, `saveLayer`, blur ni paquetes gráficos. El objetivo de 60 fps no se considera demostrado por los widget tests.

**Accesibilidad y movimiento.** Los datos originales permanecen en el formulario; cada gráfico expone un resumen semántico con valores, y los controles normales conservan foco/teclado. Etiquetas y cifras son widgets escalables; los símbolos del canvas heredan tipografía y `TextScaler`. En esta versión de Flutter, `disableAnimations` y el indicador iOS `reduceMotion` son distintos: se atienden ambos, incluidos cambios en ejecución. Reynolds detiene su controlador con cualquiera de ellos, con pausa manual, velocidad cero, `TickerMode` deshabilitado o app fuera de primer plano; elimina observers/controlador al cerrar. La vista estática conserva trayectorias y datos. La apertura de la superficie también evita la transición cuando se solicita movimiento reducido.

**Límites reales.** Los sliders exploran rangos finitos declarados y no sustituyen la entrada manual; el valor original fuera de rango no se modifica hasta la interacción. La proyección 3D no conserva longitudes/ángulos en pantalla. No se modelan cargas del divisor ni se simula flujo real. Quedan pendientes TalkBack/VoiceOver y rendimiento sostenido en dispositivos físicos, además del runner Chrome ya documentado. La capa añade cero dependencias, sin framework universal porque las cuatro escenas tienen geometrías naturalmente distintas.

**Validación de Phase 5.** 363 casos Flutter previos conservados y 34 nuevos (397 total); 247 casos de dominio sin cambios pasan en Dart y dart2js/Node. Los nuevos tests cubren mappers, coordenadas finitas, extremos, los 33 prefijos, controles/unidades, texto al 200% en claro/oscuro, tablet, teclado, semántica y contraste. Comprueban además que un tick mantiene la misma instancia de painter sin notificar al ViewModel, pausa/reanudación, ambas señales de movimiento reducido, app en segundo plano, `TickerMode` y dispose. Las cuatro capturas estáticas se revisaron visualmente. El smoke del emulador llegó a Home y su árbol accesible, pero la pérdida de conexión ADB impidió completar los pilotos; no se afirma validación física ni 60 fps medidos.

Validación JavaScript alternativa: `dart compile js tool/test_domain_web.dart -o build/domain_checks.js` seguido de `node build/domain_checks.js` ejecuta los mismos casos con dart2js sin necesitar arrancar CanvasKit o el runner de navegador. Una salida correcta no produce errores; cualquier caso fallido termina el proceso con fallo. Esto comprueba la semántica numérica web, no sustituye pruebas visuales del navegador.
